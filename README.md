# Order Management API

A .NET 10 order management REST API: customers register, browse products and place orders; admins manage products and move orders through their lifecycle. Built as a database-first portfolio project with ASP.NET Core controllers, EF Core 10 on MySQL 8.4, JWT authentication with refresh tokens, FluentValidation and Serilog.

## Architecture

```
            Api            controllers, auth setup, ProblemDetails, Swagger, Program.cs
           /    \
          v      v
 Infrastructure   Application      Api depends on both
 (EF Core, DbUp,    (services, DTOs, validators,
  JWT, repos)        interfaces)
          \      /
           v    v
            Domain          entities, behavior rules, domain exceptions (no packages)
```

Dependencies point inwards: `Api -> Application, Infrastructure`, `Infrastructure -> Application, Domain`, `Application -> Domain`. Application defines the interfaces (repositories, `IUnitOfWork`, `ICurrentUser`); Infrastructure implements them. Domain never reads the clock; the current time is passed in.

## Database-first workflow

The SQL schema is the source of truth, and the EF Core model is generated from it.

- Schema scripts live in `database/migrations/NNNN_name.sql`. They are embedded in the Infrastructure assembly and applied by DbUp at startup (Development and Docker environments). A committed script is never edited.
- Entities (`src/OrderManagement.Domain/Entities`) and `AppDbContext` are generated and start with an `<auto-generated>` header. Never edit them by hand.
- Business rules live in the hand-written `<Entity>.Behavior.cs` partials. Services change entities only through those methods.

To change the schema:

1. Add `database/migrations/NNNN_description.sql`.
2. If the script adds a new table, also add it to the `--table` list in `scripts/scaffold.ps1` (the list is hardcoded, so a missing table is silently left out of the model).
3. Run `scripts/scaffold.ps1` (needs Docker; it starts a throwaway MySQL container and regenerates the model).
4. Update the behavior partials and tests.
5. Commit the script and the regenerated code together.

## Run with Docker

```
cp .env.example .env       # then edit every value; the signing key needs at least 32 characters
docker compose up --build
```

- API: http://localhost:5080 (Swagger UI at `/swagger`, health at `/health`). Inside the container the app listens on 8080; compose publishes it on host port 5080, bound to `127.0.0.1` only. That binding avoids an older Docker Desktop bug where its IPv6 forwarder accepts `localhost` (`::1`) connections and then resets them (`ERR_CONNECTION_RESET`). To use another port, change `5080` in the `ports` entry of `docker-compose.yml`.
- The `Docker` environment applies the schema and seeds an admin user (`Seed__AdminEmail` / `Seed__AdminPassword` from `.env`) and 5 sample products.
- MySQL is published on `127.0.0.1:3308` for database tools such as SQLyog, MySQL Workbench or DBeaver. Log in with `MYSQL_USER` / `MYSQL_PASSWORD` (or `root` / `MYSQL_ROOT_PASSWORD`) from `.env`, database `MYSQL_DATABASE`.
- `docker compose down -v` stops everything and deletes the database volume.

## Run locally

Start a MySQL 8.4 instance, then store the secrets for the API project:

```
dotnet user-secrets set "ConnectionStrings:Default" "server=localhost;port=3306;database=ordermanagement;user=root;password=<password>" --project src/OrderManagement.Api
dotnet user-secrets set "Jwt:SigningKey" "<at least 32 characters>" --project src/OrderManagement.Api
dotnet user-secrets set "Seed:AdminEmail" "admin@example.com" --project src/OrderManagement.Api
dotnet user-secrets set "Seed:AdminPassword" "<admin password>" --project src/OrderManagement.Api
dotnet run --project src/OrderManagement.Api
```

The `Development` environment applies the schema and seeds the data on startup. The database itself must already exist: DbUp does not create it. Docker Compose creates it through `MYSQL_DATABASE`; locally, create it first (for example `CREATE DATABASE ordermanagement;`).

## Tests

```
dotnet test
```

Unit tests need nothing. Integration tests start a MySQL container with Testcontainers, so **Docker must be running**.

To run a single test or class, target one test project:

```
dotnet test --project tests/OrderManagement.UnitTests --filter "FullyQualifiedName~OrderTests"
```

The solution uses the Microsoft.Testing.Platform runner. `--filter "FullyQualifiedName~<Name>"` works, but if you leave out `--project`, every test project runs, the ones with no match report "zero tests ran" and the run exits with code 8. Pass `--project` (or `--ignore-exit-code 8`) to avoid that. The native filters also work, for example `--filter-method "*Cancel*"` or `--filter-class "*OrderTests"`.

## API overview

All routes are under `/api/v1`. Errors are RFC 9457 ProblemDetails with a `traceId`.

| Group | Endpoints |
|---|---|
| Auth | `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` |
| Customers | `GET/PUT /customers/me`; admin: `GET /customers`, `GET /customers/{id}` |
| Products | `GET /products`, `GET /products/{id}` (public); admin: `POST`, `PUT`, `DELETE` |
| Orders | `POST /orders`, `GET /orders/my`, `GET /orders/{id}`, `POST /orders/{id}/cancel` and `/complete`; admin: `GET /orders`, `POST /orders/{id}/confirm`, `/ship`, `/deliver` |
| Health | `GET /health` (no `/api/v1` prefix) |

Order status flow: `Pending -> Confirmed -> Shipped -> Delivered -> Completed`. Cancelling is allowed from `Pending` or `Confirmed` and restores the stock.

## Troubleshooting

**Integration tests fail with a Docker API version error.** Older Docker Engines (for example 20.10, API 1.41) are older than the API version Testcontainers 4.16 asks for. Tell the Docker client which version to use:

```
DOCKER_API_VERSION=1.41 dotnet test            # bash
$env:DOCKER_API_VERSION = "1.41"; dotnet test  # PowerShell
```

Upgrading Docker Engine removes the need for this.
