# Order Management API

A .NET 10 order management REST API: customers register, browse products and place orders; admins manage products and move orders through their lifecycle. Built as a database-first portfolio project with ASP.NET Core controllers, EF Core 10 on MySQL 8.4, JWT authentication with refresh tokens, FluentValidation and Serilog.

## Architecture

```
            Api            controllers, auth setup, ProblemDetails, Swagger, Program.cs
           /    \
          v      v
 Infrastructure   Application      Api depends on both
 (EF Core, DbUp,    (services, DTOs, validators,
  JWT, repos)        interfaces)
          \      /
           v    v
            Domain          entities, behavior rules, domain exceptions (no packages)
```

Dependencies point inwards: `Api -> Application, Infrastructure`, `Infrastructure -> Application, Domain`, `Application -> Domain`. Application defines the interfaces (repositories, `IUnitOfWork`, `ICurrentUser`); Infrastructure implements them. Domain never reads the clock; the current time is passed in.

## Database-first workflow

The SQL schema is the source of truth, and the EF Core model is generated from it.

- Schema scripts live in `database/migrations/NNNN_name.sql`. They are embedded in the Infrastructure assembly and applied by DbUp at startup (Development and Docker environments). A committed script is never edited.
- Entities (`src/OrderManagement.Domain/Entities`) and `AppDbContext` are generated and start with an `<auto-generated>` header. Never edit them by hand.
- Business rules live in the hand-written `<Entity>.Behavior.cs` partials. Services change entities only through those methods.

To change the schema:

1. Add `database/migrations/NNNN_description.sql`.
2. If the script adds a new table, also add it to the `--table` list in `scripts/scaffold.ps1` (the list is hardcoded, so a missing table is silently left out of the model).
3. Run `scripts/scaffold.ps1` (needs Docker; it starts a throwaway MySQL container and regenerates the model).
4. Update the behavior partials and tests.
5. Commit the script and the regenerated code together.

## Run with Docker

```
cp .env.example .env       # then edit every value; the signing key needs at least 32 characters
docker compose up --build
```

- API: http://localhost:5080 (Swagger UI at `/swagger`, health at `/health`). Inside the container the app listens on 8080; compose publishes it on host port 5080, bound to `127.0.0.1` only. That binding avoids an older Docker Desktop bug where its IPv6 forwarder accepts `localhost` (`::1`) connections and then resets them (`ERR_CONNECTION_RESET`). To use another port, change `5080` in the `ports` entry of `docker-compose.yml`.
- The `Docker` environment applies the schema and seeds an admin user (`Seed__AdminEmail` / `Seed__AdminPassword` from `.env`) and 5 sample products.
- MySQL is published on `127.0.0.1:3308` for database tools such as SQLyog, MySQL Workbench or DBeaver. Log in with `MYSQL_USER` / `MYSQL_PASSWORD` (or `root` / `MYSQL_ROOT_PASSWORD`) from `.env`, database `MYSQL_DATABASE`.
- CORS: browsers may call the API from the origins in `Cors:AllowedOrigins`. `appsettings.Development.json` and `appsettings.Docker.json` allow `http://localhost:4200` (the Angular dev server); the base settings allow none. To allow another origin, set `Cors__AllowedOrigins__0=https://ui.example.com` in `.env` (an origin has no path, no trailing slash and no wildcard; the app refuses to start otherwise). Bearer tokens only, so cookies are not allowed.
- `docker compose down -v` stops everything and deletes the database volume.

## Run locally

Start a MySQL 8.4 instance, then store the secrets for the API project:

```
dotnet user-secrets set "ConnectionStrings:Default" "server=localhost;port=3306;database=ordermanagement;user=root;password=<password>" --project src/OrderManagement.Api
dotnet user-secrets set "Jwt:SigningKey" "<at least 32 characters>" --project src/OrderManagement.Api
dotnet user-secrets set "Seed:AdminEmail" "admin@example.com" --project src/OrderManagement.Api
dotnet user-secrets set "Seed:AdminPassword" "<admin password>" --project src/OrderManagement.Api
dotnet run --project src/OrderManagement.Api
```

The `Development` environment applies the schema and seeds the data on startup. The database itself must already exist: DbUp does not create it. Docker Compose creates it through `MYSQL_DATABASE`; locally, create it first (for example `CREATE DATABASE ordermanagement;`).

## Tests

```
dotnet test
```

Unit tests need nothing. Integration tests start a MySQL container (and, for the policy search tests, a Qdrant container) with Testcontainers, so **Docker must be running**. The first run pulls the images. No test needs Ollama, an LLM key or the internet.

To run a single test or class, target one test project:

```
dotnet test --project tests/OrderManagement.UnitTests --filter "FullyQualifiedName~OrderTests"
```

The solution uses the Microsoft.Testing.Platform runner. `--filter "FullyQualifiedName~<Name>"` works, but if you leave out `--project`, every test project runs, the ones with no match report "zero tests ran" and the run exits with code 8. Pass `--project` (or `--ignore-exit-code 8`) to avoid that. The native filters also work, for example `--filter-method "*Cancel*"` or `--filter-class "*OrderTests"`.

## API overview

All routes are under `/api/v1`. Errors are RFC 9457 ProblemDetails with a `traceId`.

| Group | Endpoints |
|---|---|
| Auth | `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` |
| Customers | `GET/PUT /customers/me`; admin: `GET /customers`, `GET /customers/{id}` |
| Products | `GET /products`, `GET /products/{id}` (public); admin: `POST`, `PUT`, `DELETE` |
| Orders | `POST /orders`, `GET /orders/my`, `GET /orders/{id}`, `POST /orders/{id}/cancel` and `/complete`; admin: `GET /orders`, `POST /orders/{id}/confirm`, `/ship`, `/deliver` |
| Assistant | customer: `POST /assistant/chat` (see below) |
| Policies | any signed-in user: `POST /policies/ask`; admin: `POST /policies/reindex` (see "Policy Q&A") |
| Health | `GET /health` (no `/api/v1` prefix) |

Order status flow: `Pending -> Confirmed -> Shipped -> Delivered -> Completed`. Cancelling is allowed from `Pending` or `Confirmed` and restores the stock.

## Order assistant

A signed-in **customer** can ask about their own orders in plain language. A model chooses between two read-only tools, and the backend runs them:

- `get_order_status(orderNumber)`: one order's status, dates, total and items
- `list_my_orders(status?)`: up to 10 recent orders

```
POST /api/v1/assistant/chat
Authorization: Bearer <customer access token>
{ "message": "What is the status of ORD-20261023-AB12CD?" }

200 { "reply": "Your order ORD-20261023-AB12CD is Pending ..." }
```

**Security model:** whatever the model puts in a tool call is treated as untrusted input. Every call passes a backend gate that checks the tool allowlist and the strict arguments, then runs the tool as the user in the JWT. The ownership rule is the same one the REST API uses, so asking about another customer's order number returns "Order not found." exactly like a missing order. Only a restricted result reaches the model, with no internal IDs, prices per line, address or other customers' data. This holds for every provider below.

### Choosing a provider

One provider is active at a time, chosen with `Assistant__Provider` in `.env` (or `Assistant:Provider` in configuration). Switch by changing it, adding that provider's key or endpoint, and running `docker compose up -d`.

| `Assistant__Provider` | Credential | Model setting (default) |
|---|---|---|
| `Claude` (default) | `ANTHROPIC_API_KEY` | `Assistant__Claude__Model` (`claude-haiku-5-5`) |
| `OpenAI` | `OPENAI_API_KEY` | `Assistant__OpenAI__Model` (`gpt-5-mini`) |
| `Gemini` | `GEMINI_API_KEY` | `Assistant__Gemini__Model` (`gemini-3.5-flash`) |
| `Ollama` | `Assistant__Ollama__Endpoint` (no key) | `Assistant__Ollama__Model` (`qwen2.5:7b`) |

- **Check the OpenAI and Gemini model names.** Those two defaults were not confirmed against the providers' official model lists. A wrong name makes the provider answer 404, which shows up as a 500 with the cause in the log. Set the setting above to a model from the provider's current list.
- Without the selected provider's key (or the Ollama endpoint) the endpoint returns 503 "Assistant is not configured." and the rest of the API works normally. A provider outage, timeout or rate limit returns 503 "Assistant is temporarily unavailable."
- Other settings live in the `Assistant` section of `appsettings.json`: `MaxTokens` (4096) and `MaxToolRounds` (5).
- Optional overrides, mainly for tests: `ANTHROPIC_BASE_URL`, and `Assistant__OpenAI__Endpoint` (which also lets you point at an OpenAI-compatible server). Anyone who can set configuration can redirect the model traffic with these, and redirecting also sends that provider's API key to the new host. An `http://` address sends the key unencrypted, so use `https://` (loopback addresses are fine for local tests). Treat them as deployment-only settings.
- Locally, set secrets with `dotnet user-secrets set "OPENAI_API_KEY" "<key>" --project src/OrderManagement.Api`.

**Your data goes to the provider you pick.** With `Claude`, `OpenAI` or `Gemini`, the customer's free-text message, plus the order numbers, dates, status, totals and product names the tools return, are sent to that company's API. Choose accordingly.

### Ollama on another machine

Ollama runs on a separate computer; this project only needs its address.

1. On the Ollama machine, make it listen on the network: set the environment variable `OLLAMA_HOST=0.0.0.0` and restart Ollama.
2. Allow inbound TCP port **11434** in that machine's firewall (Windows Defender Firewall: new inbound rule).
3. Pull a model that **supports tool calling**: `ollama pull qwen2.5:7b` (about 8 GB of RAM).
4. In `.env` set `Assistant__Provider=Ollama` and `Assistant__Ollama__Endpoint=http://<that-machine-IP>:11434`, then `docker compose up -d`.

Each call to Ollama times out after 60 seconds. A cold model load or a slow CPU can exceed that, which shows up as 503 "temporarily unavailable": warm the model first (`ollama run qwen2.5:7b`) or use a smaller one. Ollama has **no authentication**, and the traffic is plain HTTP. Use it only on a network you trust. Small models sometimes send malformed tool arguments or pick the wrong tool; the backend rejects bad arguments and the model retries, so answers can be worse but access is never widened.

### Manual check with a real provider

Log in as a customer who has an order, then:

```
curl -s http://localhost:5080/api/v1/assistant/chat -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" -d '{"message":"What are my recent orders?"}'
```

The automated tests never call a real provider: they use scripted fakes and local stub servers.

## Policy Q&A (RAG)

Any signed-in user can ask about the shop's **cancellation, refund and shipping policies**. The answer comes only from excerpts of the Markdown files in `policies/`, and the response lists the files and sections it used. The feature never reads order data: "can *I* cancel *my* order ORD-123?" is answered with the rule, not with a decision about that order.

```
Indexing (startup, or POST /policies/reindex)
  policies/*.md -> split by heading -> embed each chunk (Ollama, Laptop B) -> Qdrant (vectors + text + metadata)
                                    \-> in-memory BM25 keyword index

Asking (POST /policies/ask)
  question -> embed (same model) -> Qdrant top 8 \
           -> BM25 keyword top 8 ----------------- RRF fusion -> top 4 chunks -> LLM (answer + [n] citations)
```

The LLM is told to answer only from the numbered excerpts and to say so when they do not contain the answer. Citations are built by the backend from the `[n]` markers in the answer (each citation carries its `number`), so a made-up source or number never reaches the response: markers with no excerpt behind them are removed from the answer text.

### Setup

1. **Laptop B (embeddings).** Install Ollama, then `ollama pull qwen3-embedding:0.6b`. Make it listen on the network: set `OLLAMA_HOST=0.0.0.0` before starting it, and allow TCP port 11434 through the firewall. Ollama has **no authentication** and uses plain HTTP, so use it only on a trusted network.
2. **Laptop A (this project).** In `.env` set `Policies__Embedding__Endpoint=http://<LaptopB-IP>:11434`. Pick the answer LLM with `Assistant__Provider` as for the order assistant (the same key and model settings are used).
3. `docker compose up --build -d` starts MySQL, **Qdrant** and the API. Qdrant keeps its index in the `qdrant-data` volume, so it survives restarts. Its dashboard is at http://localhost:6333/dashboard (bound to `127.0.0.1`).

Without `Policies__Embedding__Endpoint` the endpoint answers 503 "Policy search is not configured." and the rest of the API works normally.

### Indexing

- The API indexes `policies/` once in the background when it starts (`Development` and `Docker` environments). If Qdrant or Laptop B is down the API still starts and logs a warning; questions answer 503 until an index succeeds.
- After editing, adding or removing a file in `policies/`, re-index as an admin:

```
curl -s -X POST http://localhost:5080/api/v1/policies/reindex -H "Authorization: Bearer <admin token>"
```
```json
{ "added": 1, "updated": 2, "unchanged": 27, "deleted": 0, "totalChunks": 30 }
```

Re-indexing is idempotent. Each chunk has an ID derived from its file, heading path and part, plus a fingerprint of its text and the embedding model. A second run with no edits reports everything `unchanged` and makes no call to Ollama. An edited section is `updated`, a new one `added`, and a removed heading or file is `deleted`. A renamed file is a delete plus an add, never a duplicate. Changing `Policies__Embedding__Model` re-embeds everything. If the new model produces a different vector size, delete the Qdrant collection (or change `Policies__Qdrant__Collection`) and re-index.

To add a policy, create a Markdown file in `policies/` with a `# Title` and `##` sections (levels 1 to 3 split the file; each section needs some text), then re-index. In Docker the folder is mounted read-only from `./policies`.

### Examples

```
curl -s http://localhost:5080/api/v1/policies/ask -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" -d '{"question":"Can I cancel my order after it has shipped?"}'
```
```json
{
  "answer": "No. An order can only be cancelled while it is Pending or Confirmed. Once it is Shipped, Delivered or Completed it can no longer be cancelled; after delivery you can use the return process in the Refund Policy instead [1].",
  "citations": [
    { "number": 1, "source": "cancellation.md", "title": "Cancellation Policy",
      "section": "Cancellation Policy > When an order can be cancelled",
      "excerpt": "An order can be cancelled while its status is **Pending** or **Confirmed**. ..." }
  ]
}
```

A question the policies do not cover gets an honest answer and no citations:

```json
{ "answer": "The policies I have do not cover gift wrapping. Please contact customer support.", "citations": [] }
```

A Burmese question is answered in Burmese. Burmese text has no keyword (BM25) matches, so those questions rely on the semantic search alone, which Qwen3-Embedding handles but with less precision.

These answers are samples: the wording is the LLM's and varies. Errors are ProblemDetails: 400 for an empty or over-1000-character question, 401 without a token, 403 on `reindex` for a non-admin, and 503 with "Policy search is not configured.", "Policy search is temporarily unavailable." or "Policies have not been indexed yet."

### Running locally

`dotnet run` needs Qdrant on the machine (`docker compose up -d qdrant`), `Policies__Qdrant__Host=localhost` (the default host is the compose service name `qdrant`), and the working directory must be the repository root so `policies/` resolves. Set the secrets with user-secrets, for example `dotnet user-secrets set "Policies:Embedding:Endpoint" "http://<LaptopB-IP>:11434" --project src/OrderManagement.Api`.

### Privacy

The user's question goes to the embedding host (Laptop B) and, with the matching excerpts, to the LLM provider you chose. Policy files are not secret, but questions can contain personal details: only use providers you trust with that. The API never logs the question, the answer or policy text; it logs counts, durations, chunk IDs and exception type names.

### Tests

`dotnet test` covers the chunker, BM25, rank fusion, indexer, retriever, prompt, citations and endpoints with fakes, and the Qdrant store with a real Qdrant container (Docker needed). Checking real embeddings and a real LLM is a manual step: run the two examples above against your Laptop B and provider.

## Troubleshooting

**Integration tests fail with a Docker API version error.** Older Docker Engines (for example 20.10, API 1.41) are older than the API version Testcontainers 4.16 asks for. Tell the Docker client which version to use:

```
DOCKER_API_VERSION=1.41 dotnet test            # bash
$env:DOCKER_API_VERSION = "1.41"; dotnet test  # PowerShell
```

Upgrading Docker Engine removes the need for this.
